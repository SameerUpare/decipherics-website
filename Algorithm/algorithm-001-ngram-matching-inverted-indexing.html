Understanding N-gram Matching & Inverted Indexing

The theory, mathematics and engineering behind candidate retrieval.
Name screeningInformation retrievalPythonFoundational
Core idea: N-grams turn names into smaller searchable patterns. An inverted index maps those patterns to the records that contain them, allowing a screening system to retrieve a shortlist of candidates without comparing the query against every record.

01 · Problem

Why exact matching fails

Exact string matching works only when two names are represented in precisely the same way. Real payment and watchlist data rarely behaves so neatly.

Names can differ because of spelling variation, omitted characters, transliteration, token order, spacing, punctuation, aliases or inconsistent data entry. A direct equality check treats these variations as completely different strings.

Illustrative screening examples

Payment nameWatchlist nameWhy exact matching misses it
SAMEERSAMIRDifferent spelling and character sequence
MOHAMMEDMUHAMMADAlternative transliteration
ABDUL RAHMANABDULRAHMANSpacing variation
AL HUSSEINHUSSEIN ALToken order variation

A screening platform therefore needs a candidate retrieval mechanism: given an incoming name, find a manageable set of potentially relevant reference-list records for more detailed comparison.

Important distinction: Candidate retrieval is not the same as identity resolution. Retrieving a record means it shares one or more search patterns; it does not establish that both names refer to the same person or entity.
02 · Concept

Understanding N-grams

An N-gram is a contiguous sequence of N characters or tokens extracted from a text string. In character N-grams, a sliding window moves across the text one character at a time.

Take the name SAMEER. Using character trigrams (N = 3), the windows are SAM, AME, MEE and EER.

CHARACTER TRIGRAMS · SAMEER
SAMAMEMEEEER

Each window overlaps the previous window by N − 1 characters.

For a string of length L, the number of character N-grams is:

Number of N-grams = max(0, L − N + 1)L is the number of characters after the chosen normalisation policy; N is the gram size.

For SAMEER, L = 6. It produces five bigrams, four trigrams and three four-grams.

03 · N-gram types

Unigram, bigram, trigram and higher

The value of N controls the size of each pattern. Smaller values create more matches and usually broader retrieval; larger values create more specific patterns but can miss names with small spelling differences.

TypeNPatterns from SAMEERTypical behaviour
Unigram1S, A, M, E, E, RBroad, low discrimination
Bigram2SA, AM, ME, EE, ERMore selective than unigrams
Trigram3SAM, AME, MEE, EERCommon starting point for character retrieval
Four-gram4SAME, AMEE, MEERMore specific, less tolerant of edits
Five-gram5SAMEE, AMEERHighly specific for short names

Character N-grams vs token N-grams

Character N-grams operate inside words. Token N-grams operate on whole words or tokens. For example, the token sequence in ABDUL RAHMAN can produce the unigram tokens ABDUL and RAHMAN, and the bigram token sequence ABDUL RAHMAN.

Character N-grams

Useful for spelling variation, partial overlap and approximate name retrieval.

Token N-grams

Useful for word-level structure, multi-part names and phrase retrieval.

The implementation must define its text policy: whether spaces are retained, whether punctuation is removed, how Unicode is normalised, and whether grams can cross word boundaries. There is no universally correct policy for every name corpus.

04 · Inverted index

From N-grams to an inverted index

Generating N-grams gives us searchable features. It does not, by itself, make searching a large reference list efficient. An inverted index is a data structure that maps each term or N-gram to the records in which it occurs.

Forward representation

A forward representation stores each record and its N-grams:

S001 → SAMEER  → SAM, AME, MEE, EER
S002 → SAMIR   → SAM, AMI, MIR
S003 → SAMEERA → SAM, AME, MEE, EER, ERA

Inverted representation

The inverted index reverses the relationship. Each N-gram points to a posting list: the collection of record identifiers containing that gram.

N-gramPosting list (record IDs)
SAMS001, S002, S003
AMES001, S003
MEES001, S003
EERS001, S003
AMIS002
MIRS002
ERAS003
Why “inverted”? The lookup direction is reversed. Instead of asking “which N-grams belong to this record?”, the search asks “which records contain this N-gram?”

What is stored in a posting list?

A basic posting list stores record IDs. A production index may also store term frequency, field name, token position, offsets, document frequency or other metadata needed for ranking and filtering. The right structure depends on the retrieval design.

05 · Working

Index construction and candidate retrieval

There are two distinct workflows: building or updating the index, and using it to retrieve candidates for an incoming screening query.

A. Build the index

1
Load reference records

Read the names and stable record identifiers from the watchlist or reference database.

2
Normalise text

Apply the chosen case, Unicode, punctuation, whitespace and tokenisation policy consistently.

3
Generate N-grams

Generate the selected character and/or token N-grams for each searchable name field.

4
Populate posting lists

For every distinct gram in a record, add that record's ID to the gram's posting list.

5
Store index statistics

Maintain document frequency and, where required, term frequencies and weights.

B. Retrieve candidates

1
Receive a query

For example, an incoming payment party name: SAMEER.

2
Apply the same normalisation and N-gram policy

Generate SAM, AME, MEE and EER.

3
Look up each gram

Fetch the posting list associated with each query gram from the inverted index.

4
Aggregate and deduplicate

Count or weight the number of query grams shared by each retrieved record.

5
Apply retrieval rules and rank

Use overlap, IDF weighting or another retrieval score to select a candidate set for downstream matching.

Worked retrieval example

Query: SAMEER. The query produces four trigrams. Looking up those four grams returns the following illustrative overlap counts:

CandidateShared query gramsOverlap count
S001 · SAMEERSAM, AME, MEE, EER4
S002 · SAMIRSAM1
S003 · SAMEERASAM, AME, MEE, EER4

S001 and S003 tie on this simple overlap count. A later comparison stage can distinguish them using full-string similarity, token information and identity attributes.

Retrieval is a filter, not a verdict. A record that shares several N-grams is a candidate for further examination. It is not automatically a match. Conversely, a record with no shared grams may be missed by this retrieval channel, which is why multiple retrieval strategies and recall testing matter.
06 · Mathematics

Similarity, overlap and term weighting

After retrieving records, a system may measure how much the query and candidate representations overlap. These scores describe similarity between representations; they are not probabilities that two names belong to the same person.

A. Jaccard similarity

Jaccard measures the size of the intersection divided by the size of the union of two N-gram sets.

J(A,B) = |A ∩ B| / |A ∪ B|A and B are sets of unique N-grams. The result ranges from 0 to 1.

For SAMEER and SAMIR, the trigram sets are:

A = {SAM, AME, MEE, EER}
B = {SAM, AMI, MIR}

Intersection = {SAM}             → 1
Union        = {SAM, AME, MEE, EER, AMI, MIR} → 6

Jaccard = 1 / 6 = 0.1667

B. Dice coefficient

Dice gives twice the weight to the intersection relative to the total size of both sets.

Dice(A,B) = 2 × |A ∩ B| / (|A| + |B|)For the SAMEER / SAMIR example: 2 × 1 / (4 + 3) = 0.2857.

C. Cosine similarity

Cosine compares two N-gram vectors. Each dimension represents a gram; its value can be a binary indicator, frequency or a weight such as TF-IDF.

cos(A,B) = (A · B) / (||A|| × ||B||)Vector representation makes it possible to account for gram frequencies and weights rather than only set membership.

D. Inverse document frequency (IDF)

Common grams often carry less identifying information than rare grams. IDF assigns lower weight to grams found in many records and higher weight to less common grams.

IDF(g) = log(N / DF(g))N = number of indexed records; DF(g) = number of records containing gram g. Smoothing is often added in practical implementations.

A common smoothed variant is:

IDF(g) = log(1 + (N / (1 + DF(g))))

For example, if a trigram appears in 50,000 of 1,000,000 indexed records, it is less discriminative than a trigram appearing in only 20 records. IDF can help reduce the influence of very common patterns.

Keep the concepts separate: N-gram generation creates the features. An inverted index makes those features searchable. Jaccard, Dice and Cosine compare representations. IDF weights features according to how widely they occur in the corpus.

07 · Examples

Simple, medium and complex cases

Example 1 · Simple: exact spelling

Compare SAMEER with SAMEER using trigrams.

A = {SAM, AME, MEE, EER}
B = {SAM, AME, MEE, EER}

Intersection = 4
Union = 4
Jaccard = 4 / 4 = 1.00

The representations are identical under this normalisation and gram-size policy. This says nothing by itself about whether the real-world identity is the same; names are not unique identifiers.

Example 2 · Medium: spelling variation

Compare SAMEER with SAMIR.

A = {SAM, AME, MEE, EER}
B = {SAM, AMI, MIR}

Common grams = {SAM}
Union size = 6
Jaccard = 1 / 6 = 0.1667

Only one trigram overlaps. A strict trigram overlap threshold could fail to retrieve this candidate. A multi-channel system could add phonetic retrieval, smaller grams or edit-distance-based retrieval to improve coverage.

Example 3 · Complex: transliteration variation

Consider MOHAMMED ALI and MUHAMMAD ALI. These spellings may be transliteration variants of a name, but a basic character trigram index does not understand that linguistic relationship. It only sees character sequences.

A stronger retrieval design can:

  • Normalise Unicode consistently and preserve the original source value.
  • Generate character N-grams from the original and approved transliteration variants.
  • Index tokens and useful token combinations separately.
  • Use phonetic or language-aware retrieval where appropriate.
  • Merge and deduplicate candidates from the different retrieval channels.
  • Evaluate whether known true matches are being retrieved, not just whether the returned names look similar.
Engineering lesson: A single N-gram configuration is unlikely to provide sufficient recall across every script, language, name length and transliteration convention. Retrieval should be evaluated against representative, labelled data.
08 · AML application

Using N-grams in sanctions and payment screening

In payment screening, a system extracts relevant parties from a payment message and compares them with sanctions, watchlist or other reference data. For an ISO 20022 payment, relevant parties may include the debtor, creditor and agents or intermediaries, depending on the screening policy and message flow.

Illustrative flow

1
Payment ingestion

Receive a payment message such as pacs.008 and extract the party names and available identifiers.

2
Normalisation

Standardise the searchable representation while retaining the original name for audit and investigation.

3
Candidate retrieval

Generate N-grams and query the inverted index, alongside other retrieval channels.

4
Feature calculation

Calculate name similarity and compare additional available attributes such as date of birth, country and identifiers.

5
Scoring and disposition

Apply the approved matching policy and risk framework to support clearance, investigation or escalation.

Where N-grams fit

Pipeline stageRole
Candidate retrievalPrimary use Find reference records sharing character patterns.
Feature engineeringProvide overlap or weighted-overlap features for downstream scoring.
Candidate rankingContribute to ranking when combined with other retrieval signals.
Final decisionNot sufficient on its own to establish a true match or justify a block.

How to measure retrieval quality

Recall@K

Of all known relevant matches, what proportion appears in the top K retrieved candidates?

Precision@K

Of the top K retrieved candidates, what proportion is relevant?

Candidate volume

How many candidates proceed to detailed matching and investigation?

Latency

How long does index lookup and candidate aggregation take?

For a screening retrieval layer, missing a genuine match can be more serious than retrieving extra candidates. Thresholds therefore need to be selected using labelled data, operational capacity and the institution's risk appetite. Candidate reduction should never be optimised at the expense of unacceptable recall.

09 · Limitations

Where N-gram retrieval can fail

LimitationWhy it mattersPotential mitigation
Short namesVery few grams are available; one edit can change much of the representation.Adaptive gram sizes and other retrieval channels.
TransliterationDifferent scripts or spellings may share few or no character grams.Language-aware transliteration and multilingual retrieval.
Common gramsFrequent grams create large posting lists and noisy candidates.IDF weighting, stop-gram policies and ranking.
Token orderCharacter grams do not inherently understand name-part order.Token-based features and order-insensitive matching.
Boundary policyRemoving spaces can create grams across word boundaries; retaining them can make spacing changes disruptive.Explicit and consistently applied field/token policies.
Index maintenanceNew, amended or deleted list entries must be reflected correctly.Incremental updates, versioning and reconciliation.
Threshold selectionRestrictive thresholds can silently exclude true candidates.Measure recall on representative labelled datasets.
Resource useLarge posting lists and many gram variants increase storage and query work.Compression, partitioning, pruning and query planning.

Indexing improves the search process, but it does not remove the need to design for recall, data quality, update consistency, explainability and operational monitoring.

10 · Alternatives

Related and more advanced approaches

TechniqueWhat it contributesHow it relates
TF-IDFWeights grams by their frequency in a record and rarity across the corpus.Builds on N-gram features.
BM25Ranks records using term-frequency saturation and document-length normalisation.Information-retrieval ranking approach; often token-oriented, adaptable to gram terms.
MinHashCreates compact signatures that estimate set similarity.Can reduce the cost of approximate set-similarity search.
Locality-Sensitive Hashing (LSH)Maps similar representations into buckets with higher probability than dissimilar ones.Approximate retrieval; trades exactness for speed and scale.
Phonetic algorithmsEncode pronunciation-related patterns.Complement character-based retrieval, especially for spelling variation.
EmbeddingsRepresent text as vectors that can capture broader linguistic patterns.Alternative or additional retrieval channel; not proof of identity.
Practical design: A robust screening system can combine character N-grams, phonetic retrieval, transliteration and token-based retrieval. Merge the candidate sets, then use richer identity features and controlled decision logic downstream. No single retrieval technique should be assumed to cover every relevant match.
11 · Key takeaways

When and why to use N-gram matching

  • N-grams break strings into overlapping character or token sequences.
  • An inverted index maps each N-gram to the records containing it.
  • Posting lists make it possible to retrieve candidate records through index lookups rather than scanning every record.
  • Similarity measures such as Jaccard, Dice and Cosine compare representations; they are not identity probabilities.
  • IDF weighting reduces the influence of common patterns and emphasises more discriminative grams.
  • Retrieval quality must be measured with recall, precision, candidate volume and latency.
  • AML screening requires multiple retrieval channels and downstream identity assessment; N-gram overlap alone cannot establish a sanctions match.

The central engineering principle

Use N-grams to find candidates. Use an inverted index to find them efficiently. Use richer evidence and governed decision logic to assess whether they matter.
